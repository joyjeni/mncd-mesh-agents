## Summary

MNCD proposes a decentralized, gossip-based, replicated multi-agent LLM mesh and reports a 44.0%→97.5% tool-selection accuracy improvement over a single-agent baseline, near-lossless degradation under 40% agent failure or 20% packet loss, and a 93.3% vs. 53.3% lift on a Karnataka agricultural-pricing scenario. I read the manuscript, README, `src/mesh.py`, `src/agents.py`, `src/eval.py`, both results tables, and `metrics/results.json`, and additionally executed the repository's own evaluation code directly to check its behavior rather than relying solely on static reading. From the standpoint of agent-orchestration benchmarking practice — the area in which I evaluate agentic frameworks daily — this manuscript's central empirical claims do not hold up under construct-validity scrutiny. The "ToolBench-syn" benchmark is not a scaled-down version of real ToolBench; it is a categorically simpler multiple-choice task (8 near-random synthetic distractors drawn from 16 hand-authored category templates) that has no relationship to ToolBench's actual difficulty profile (16,000+ real, semantically overlapping REST APIs requiring multi-step DFSDT reasoning), which fully explains why MNCD's reported 97.5% so dramatically exceeds ToolLLaMA's real 66.7% pass rate — the two numbers are not measuring comparable difficulty, let alone the same task. Separately, the paper's "Borda consensus" is, on inspection of `consensus_pick()`, not Borda count at all: it sums raw continuous LLM confidence scores rather than converting agent outputs into ranks first, which is a different (and less well-motivated for cross-agent-scale-invariance) aggregation rule than the one described in the paper's own equation. The paper provides no mechanism anywhere in the repository for converting free-text LLM outputs into a rankable candidate set, which is a load-bearing gap given that the notebook's real backbones (Gemma/Qwen/Llama) generate free text, not the numeric scores `MockLLM` fabricates. Reproducibility is further limited by the complete absence of a pinned dependency file and by the fact that the committed results were never actually produced by the three named LLM backbones. Finally, every experiment uses exactly 5 agents; there is no evidence bearing on how the architecture behaves at 10, 20, or more agents, which matters directly for any claim about a decentralized mesh's practical advantage over a centralized coordinator (that advantage should, if real, become more pronounced — not less — as agent count grows).

## Strengths

- **Correctly diagnoses a real problem in the agent-orchestration literature.** AutoGen's GroupChat manager, MetaGPT's SOP pipeline, and LangGraph's directed-graph checkpointing genuinely do concentrate coordination state in one or two privileged components; the architectural critique in §I and §VI (Related Work) is accurate to how these frameworks actually work, based on my own familiarity with their source and documentation.
- **The mesh transport is framework-agnostic by design**, exposing a plain `LLMBackbone` interface that in principle could be benchmarked against AutoGen/LangGraph/CAMEL on equal footing if the authors chose to instrument those frameworks' own agents behind the same interface — a good design decision for future comparative work, even though it is not yet exploited.
- **The Weighted Borda–style aggregation formula, as written in the paper (`README.md` §"Core Equations"), is a reasonable design** if implemented as stated (rank-based, not score-based) — Borda-style rank aggregation is a legitimate, well-studied choice for combining multiple rankers when individual scores are not directly comparable across agents.
- **The paper is honest about the live-data gap in its Limitations section**, explicitly noting the Karnataka `data.gov.in` endpoint returned empty results at evaluation time — this candor is appropriate even though (per Cross-Checks below) it should be surfaced earlier than the Limitations section.
- **The distress-threshold design (τ=0.55) is a sensible, simple mechanism in concept** — confidence-gated help-seeking is a reasonable pattern in agent orchestration and is consistent with practices like LangGraph's conditional routing or AutoGen's nested-chat escalation, even though (see Detailed Comments) it is not shown to function in this evaluation.

## Weaknesses

- **"ToolBench-syn" inflates accuracy by construct-simplification, not by architectural merit.** The synthetic fixture (`make_synthetic_toolbench`) draws 8 candidate tools per query from 16 hand-written category templates (e.g., `Finance_API_0`…`Finance_API_7`), with the gold tool selected uniformly at random and no semantic overlap, argument schemas, or multi-hop reasoning of any kind. Real ToolBench (Qin et al., ICLR 2024) requires selecting among candidates drawn from a corpus of 16,000+ real, often semantically overlapping REST APIs, frequently through multi-step DFSDT search. An 8-way near-uniform pick among synthetic template strings is a fundamentally easier task than a real ToolBench query, and this fully accounts for why MNCD's number (97.5%) is nearly 31 points above ToolLLaMA's real, peer-reviewed pass rate (66.7%) on the actual benchmark it is named after.
- **The paper's own "Borda consensus" equation is not what the code implements.** `consensus_pick()` in `src/agents.py` computes `score[tool] += weight * float(raw_score)` — a weighted sum of continuous LLM confidence scores — not `score[tool] += (|C| - rank(tool))`, the rank-based formula given in the README's own "Core Equations" section. These are materially different aggregation rules: score-summing is sensitive to each agent's confidence calibration and scale, while true Borda count is scale-invariant and depends only on ordinal rank. The paper should either rename the mechanism (e.g., "weighted score-sum consensus") or actually implement rank-based Borda and re-run the evaluation, since the two rules can produce different winners whenever agents' confidence distributions differ in scale (which they do here — `MockLLM` competence directly shifts the scale of the gold tool's score).
- **No mechanism exists, in the paper or the code, for converting free-text LLM output into a rankable candidate set.** `MockLLM.score_tool()` returns numeric floats directly; there is no analogous method on the real `HFBackbone` class in `notebooks/build_notebook.py` that would parse a Gemma/Qwen/Llama free-text completion into per-tool scores or ranks. Since consensus (whether Borda or score-sum) fundamentally requires this conversion, and it is entirely unspecified for the real backbones the paper claims to use, the aggregation mechanism as evaluated cannot be assumed to transfer to the real-LLM setting at all.
- **The comparison table (Table 2) juxtaposes numbers I recognize as coming from four unrelated benchmarks with no adjustment or caveat.** From my own familiarity with these papers: AutoGen's reported 69.5%-class figures come from GSM8K/MATH-style math-reasoning multi-agent debate settings, not tool selection; MetaGPT's 85.9% is a HumanEval code-generation pass@1 figure; CAMEL and LangGraph have no standard tool-selection accuracy figure to report at all (correctly marked "n/a" in the table) precisely because they are not evaluated as tool-selection systems in their original papers. Placing MNCD's number in the same column as these is a category error, not merely an SOTA-comparison presentation issue — it invites an apples-to-oranges reading regardless of caveats in prose.
- **Reproducibility is blocked by missing pinned dependencies and by the fact that no committed artifact was produced by the named models.** There is no `requirements.txt`, `environment.yml`, or `pyproject.toml` anywhere in the repository (confirmed by direct filesystem search). `metrics/results.json`'s `git_commit` field is literally the string `"n/a"`. The three HuggingFace model IDs are named in the README and instantiated in `notebooks/build_notebook.py`'s `HFBackbone` class, but no committed revision hash, quantization config verification, temperature/sampling parameters, or prompt templates are pinned or reported for that backbone — and, more fundamentally, no evidence in the repository (git history, generated timestamps, or output artifacts) indicates the notebook was ever executed to produce the reported numbers.
- **All experiments use exactly N=5 agents; there is no scalability evidence for the paper's central decentralization argument.** A mesh architecture's central selling point over a centralized coordinator is that it should degrade more gracefully and coordinate more efficiently as the agent pool grows — precisely because a coordinator becomes a bottleneck at scale while a mesh, in principle, does not. This paper never tests that claim: S1–S5 are all N=5, and the message-cost model \(O(Nk\log N)\) is asserted from citation (Demers et al.) rather than fitted to data at multiple N.

## Detailed Comments

**1. Benchmark construct validity: "ToolBench-syn" is not a faithful proxy for real ToolBench, and the ~44–97.5% MNCD range is not directly comparable to ToolLLaMA's real 66.7% pass rate.**
Real ToolBench evaluation (Qin et al., ICLR 2024) selects among candidates drawn from a live corpus of over 16,000 real-world REST APIs with genuine semantic overlap between distractors and the gold API, often requiring multi-step depth-first search over tool-calling trajectories (DFSDT). MNCD's synthetic fixture instead draws 8 candidates from 16 hand-authored category buckets (`Finance`, `Maps`, `Weather`, …) with template names like `Finance_API_3` and template descriptions like `"Finance tool 3"` — there is no semantic distractor difficulty, no multi-step reasoning, and the "gold" label is chosen uniformly at random by the fixture generator itself. A single-shot 8-way pick among near-arbitrary template strings is intrinsically a much easier classification problem than real ToolBench's retrieval-and-execution task. This is sufficient on its own to explain the entire ~31-point gap between MNCD's reported 97.5% and ToolLLaMA's real 66.7pass rate — no architectural claim is needed, or supported, by this comparison. **Verdict: the ~30–97% MNCD range is not plausible as a same-difficulty comparison to real ToolBench and should not be presented alongside real-ToolBench figures without an explicit, prominent caveat; ideally, the paper should also report accuracy on a genuine ToolBench subset (even a small one) so a same-benchmark number exists.**

**2. The paper's stated Borda-count consensus mechanism is not what is implemented, and the described mechanism itself is under-specified for free-text agent outputs.**
Borda count is designed for aggregating *ranked preference lists*, and its scale-invariance (only ordinal position matters, not the magnitude of the underlying score) is precisely why it is an appropriate choice when different voters/agents may have incomparable internal scoring scales — which is a real concern here, since the paper's own competence-heterogeneous agents (0.86 vs. 0.62) would be expected to have different confidence calibration if using real LLMs. However, `consensus_pick()` implements a weighted sum of raw scores, not rank-based Borda; this is a distinct, non-scale-invariant aggregation rule that can be dominated by whichever agent happens to produce the largest-magnitude scores, independent of whether its ranking is more accurate. Separately, and more fundamentally: nothing in the repository specifies how a real LLM's free-text completion (e.g., "I would recommend using the Finance_API_3 tool because…") would be parsed into either a numeric score or an ordinal rank suitable for either aggregation rule. `MockLLM` sidesteps this entirely by fabricating a float directly. **Verdict: the consensus mechanism as described (Borda) and as implemented (score-sum) are two different rules, and neither has a defined free-text-to-rankable-form conversion for the real backbones the paper claims to evaluate. This must be resolved before the consensus mechanism can be considered evaluated at all, let alone validated as an improvement over simpler aggregation (e.g., majority vote or a single strongest agent).**

**3. Table 2 is a category error, not merely a caveat-needing presentation choice, when checked against my own knowledge of the cited frameworks' published results.**
AutoGen's headline multi-agent results (Wu et al., COLM 2024) are reported primarily on math and coding-reasoning tasks (GSM8K/MATH-style multi-agent debate and code-generation-with-execution settings), not on a tool-selection benchmark; MetaGPT's 85.9% is specifically a HumanEval pass@1 code-generation figure (Hong et al., ICLR 2024 Oral); CAMEL (Li et al., NeurIPS 2023) and LangGraph, correctly, have no standard tool-selection accuracy number to report, which the table itself marks "n/a" — this internal inconsistency (why does the table have a numeric column at all, if two of five baselines cannot populate it with anything meaningful) is itself a signal that the column should not exist in its current numeric form. **Verdict: Table 2 constitutes a category error as currently constructed.** I concur with the distributed-systems reviewer's recommendation to convert it into a qualitative feature table, and I would add: if any numeric comparison is retained, it should be run against a framework's actual open-source implementation (AutoGen's GroupChat is the most tractable, being a pip-installable, actively maintained library with a straightforward API) reproduced on MNCD's own fixture, not lifted from each framework's original paper on a different task.

**4. Reproducibility is currently insufficient for another lab to reproduce the 97.5%/97.0%/93.3% figures, let alone any real-model figures.** No `requirements.txt`, `environment.yml`, or `pyproject.toml` exists anywhere in the repository, so even the synthetic-mock pipeline's exact Python/library versions are unpinned (a risk mainly for `datasets`/`transformers` version drift affecting the notebook path, and negligible but still present for the pure-stdlib mock path). More seriously: the 97.5%/97.0%/93.3% figures are reproducible today only because they derive from `MockLLM`'s deterministic seeded RNG, not because the paper's named backbones were pinned and re-runnable — no commit SHA, revision tag, or quantization/precision configuration is recorded anywhere for `google/gemma-2-2b-it`, `Qwen/Qwen2.5-7B-Instruct`, or `meta-llama/Llama-3.1-8B-Instruct`, and no sampling temperature, top-p, max-token, or prompt-template values are specified for any of the three. A lab attempting to reproduce "the MNCD result" using the real backbones named in the abstract would have no basis for matching the reported numbers, because those numbers were never generated by those backbones in the first place. **Required for reproducibility: (a) a pinned `requirements.txt`/lockfile; (b) recorded model revision hashes and inference hyperparameters for all three named backbones; (c) either removal of the backbone names from the abstract/README until real-backbone numbers are actually reported, or an explicit, prominent statement that all currently-reported numbers are mock-only and real-backbone numbers are pending.**

**5. Scalability claims are entirely unsupported; a minimum additional experiment is a 3-point N sweep.**
Every one of the five scenarios uses exactly 5 agents. The paper's cost-analysis section cites Demers et al.'s \(O(N k \log N)\) push-gossip result to justify an implicit scalability claim, but never fits or measures this relationship — there is exactly one data point (N=5), which cannot support any claim about scaling behavior in either direction (message cost, latency, or fault-tolerance graceful-degradation at larger N). Given that the mesh's core value proposition relative to centralized orchestrators (AutoGen, MetaGPT) is precisely that it should not bottleneck as the agent pool grows, this is not a minor gap — it is the one experiment most directly relevant to justifying the "decentralized mesh" framing over a simpler centralized alternative. **Minimum required experiment: repeat scenarios S1–S4 (or the mock-equivalent) at N ∈ {5, 10, 20, 40} with the competence pool proportionally resampled, reporting msgs/query, latency p50/p95, and accuracy retention under a proportional (~40%) agent-kill fraction at each N, and fitting the empirical message-cost curve against the theoretical \(O(Nk\log N)\) model to report a goodness-of-fit statistic. Absent this, any statement in the paper implying the architecture "scales" should be removed or explicitly qualified as untested.**

---

## Recommendation

**Major Revision**

The paper correctly identifies a real architectural gap in existing multi-agent LLM orchestration frameworks and proposes a coherent decentralized alternative. But from a benchmarking-practice standpoint, the manuscript's evaluation does not yet support its claims: the synthetic "ToolBench-syn" benchmark is not a faithful proxy for real ToolBench and its absolute numbers should not be placed alongside real ToolLLaMA figures without major caveats; the described Borda-count consensus mechanism does not match the implemented score-summing mechanism, and neither has a defined path for real free-text LLM outputs; Table 2 conflates benchmarks in a way that constitutes a category error by the standards of agent-orchestration literature I am familiar with; reproducibility is blocked by missing dependency pinning and by the fact that no committed result was produced by the paper's named backbones; and the architecture's central scalability premise is untested at any N beyond 5. None of these are fatal to the underlying idea, but each requires concrete new experiments or corrections before the paper's claims are supportable.
